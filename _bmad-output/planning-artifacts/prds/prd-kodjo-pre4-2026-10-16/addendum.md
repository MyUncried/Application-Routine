# Addendum PRD PRE-4 — indications techniques non contraignantes

Ce document accompagne `prd.md`. Il regroupe les indications techniques relevées pendant la préparation du PRD : elles viennent des sources normatives consolidées de `caa2a5cf`, de la section « Inventaire opposable PRE-4 » du ch. 13 reprise au titre de Q7 (assertions de classe T, mécanismes techniques), ou de constats faits sur le code de départ. **Elles ne lient pas l'architecture** : ce ne sont pas des exigences, et la solution technique se construit à partir du code de départ, dans les skills BMad (`CLAUDE.md`). En cas d'écart, le PRD prime. L'état des lieux complet du code de départ (`c32e360d`, code applicatif de la clôture PRE-3) est dans `extracts/code-depart.md`, à côté de ce fichier.

Les autres notes pour l'architecture restent dans le PRD, à l'endroit de l'exigence qu'elles concernent (par exemple 4.5, 4.6, 4.13, 4.17 : assertions Q7 de classe T 05.4, 06.6, 13d.4, 13n.2, 17.2, 17.6).

## Persistance, migration, copies et Médias (ED-18, ED-19, ED-21)

Ces éléments ne sont pas des exigences. Ils sont transmis pour la conception ; la solution se construit à partir du code de départ.

- **Q19 (2026-10-16)** — La migration distingue désormais l'erreur structurelle (annulation complète, FR-18-15) de l'Exercice aux paramètres illisibles (écarté avec ses liens, FR-18-20). Le choix du mécanisme (détection de l'illisibilité, suppression des liens dans la même transaction, comptage transmis à l'interface) relève de l'architecture.

- **T-01** — Le nom des champs, la forme de la représentation typée et le schéma de migration sont des choix d'implémentation (`ch09:1246`, `ch09:1230`). Seule contrainte : aucun `null` ambigu ne porte seul la distinction entre numérique et échec.
- **T-02** — Conception préalable : inventaire des énumérations et des champs existants, versionnement, lecture de l'ancien format, transformation atomique, copies et compatibilité des données enregistrées. Ne pas déclarer une migration définie avant l'inventaire du schéma réel (`ch09:1262`, `ch12:1597`).
- **T-03 / C-05** — La numérotation de migration des spécifications (« 009 prochain », `ch12:1565`, `ch11:435`) est périmée : le code de départ contient déjà neuf migrations. La numérotation se lit dans le code. `migration001.ts` ne se modifie jamais (AGENTS.md).
- **T-04** — Constat de code : l'Ancien mode À l'échec est présent dans le schéma (contraintes de `migration003.ts`, `migration004.ts`, `migration006.ts`), dans le domaine Exercice et dans le domaine Séance (`Session.ts:64`, `validation.ts`, `SessionDraft.ts`, `SqliteSessionRepository.ts:1243`). La migration et le transport touchent les deux domaines (Q4). La contrainte composite mode/cible de `migration004.ts:117-170` exige une valeur numérique en Durée et en Répétitions ; elle est incompatible avec une Cible à l'échec dans ces Modes (`extracts/code-depart.md` §9, §10.1-2).
- **T-05** — Le prérequis « collection par Série avant les Cibles et le Bip par Série » (`ch12:1553`) semble livré par PRE-3 (JSON canonique versionné à côté des colonnes historiques) ; à vérifier.
- **T-06** — Instantané : contenu immuable, format relisible après évolution du modèle, nouvelle version compatible avec les anciennes (`ch09:567`, `ch12:418-422`). Constat : `exerciseSnapshot.ts` et `parseExecutionParameters` n'acceptent que la version 1 ; aucun Instantané n'est enregistré (H11).
- **T-07** — Toute opération sur plusieurs objets liés est atomique ; les contraintes d'intégrité (zéro interdit comme Cible, simultanéité numérique/échec interdite, unicité de position des Médias) peuvent aussi être appliquées en persistance (`ch12:426-438`).
- **T-08** — Repositories séparés pour les Définitions, les Copies en Séance et les Médias ; pas d'ORM (`ch12:1357`, AGENTS.md).
- **T-09** — Erreurs : catégories de validation existantes et état invalide, avec champ et Série localisés ; aucune nouvelle API réseau (`ch11:375`).
- **T-10** — Un service de références compte les usages actifs et historiques avant tout nettoyage physique d'un Média (`ch12:1355`). Constat : le code de départ n'a aucune suppression physique et dispose d'un comptage des références.
- **T-11** — Tests de persistance : création, modification, suppression, transactions, migrations, sur SQLite réelle (`ch12:466`, `PERIM:36`). Constat : un adaptateur SQLite réel pour les tests et un mécanisme d'échec provoqué existent déjà (`extracts/code-depart.md` §4).
- **T-12** — Le moteur classera chaque phase par Mode et nature de Cible ; la forme transportée doit le permettre (`ch12:1595`). Hors périmètre.
- **T-13** — Contrôler les données réellement présentes avant livraison (`ch12:1565`), repris comme critère dans FR-18-19.
- **Section Q7, classe T** (non reprises comme exigences) : format JSON « v1/v2 » et adaptateur v1 (18m.8, 18d.3, 19s.5) ; base « v9 → v10 » et `user_version` 9 conservé après échec (18m.8, 18r.2) ; colonnes numériques nullables quand la Cible est à l'échec (18m.9), acceptables seulement en complément d'un type explicite ; `foreign_key_check` vide, empreintes de fichiers, octets identiques, injection d'un échec avant validation de la transaction (18m.10, 18r.2, 18r.4, 19n.3) ; prêts de fichiers aux Brouillons libérés selon le cycle existant (21.4).
- **Projection des colonnes historiques** — Constat : la projection vers les colonnes historiques ne reprend que la première Cible ; une première Cible à l'échec en Durée ou en Répétitions produirait une valeur nulle refusée par les contraintes actuelles (`extracts/code-depart.md` §10.2). La lecture actuelle lève une erreur si la Cible est incohérente avec le Mode (§10.4), ce qui touche FR-18-14 et FR-18-15.
